# 领域模块开发指南

每个新业务以独立模块实现 `DomainModule`，并注册明确的 `AgentAction`。动作只接收已经结构化的 `Map`/DTO 参数；模型输出、前端字段和外部 REST 报文都不能直接进入领域执行逻辑。

1. 为领域分配全局唯一且稳定的 `code`，并通过 `agentDescriptor()` 提供展示名、公开描述、白名单 `iconKey`、路由描述、路由提示和推荐问题。
2. 为动作分配稳定代码，例如 `travel.schedule.query`；动作码首段必须与所属领域 `code` 一致。
3. 使用 `ActionDescriptor` 声明模式、必填字段和确认标题。所有非 `QUERY`/`DRAFT` 动作都必须有确认标题，否则注册表会拒绝启动。
4. `QUERY`、`DRAFT` 可以直执；`COMMIT`、`PAYMENT`、`AFTER_SALE` 会被 Runtime 强制创建任务并等待确认。
5. 在 `execute` 内完成资格、状态和幂等校验，并通过适配器调用外部事实源。
6. 返回 `ActionResult`，其中卡片只包含可展示的脱敏数据。超时写操作必须返回结果未知并查单，不能直接重试。

Runtime 启动时会构建不可变 `DomainAgentRegistry`，校验 Agent code、Action code、动作前缀、公开元数据和风险模式。总 Agent 只能从可见领域中选择目标，领域 Agent 只能从本领域动作白名单中选择动作；模型即使返回另一个领域的合法动作码，也会被服务端所有权校验拒绝。

生产模块还必须提供输入 DTO 校验、JSON Schema、外部调用审计、回调验签与外部业务适配器。`RuntimeStore` 已提供内存和 JDBC 两种基础实现；新增领域事实仍应在领域模块自己的适配器与数据模型中持久化，不应塞入通用 Runtime 表。
